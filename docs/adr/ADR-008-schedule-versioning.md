# ADR-008. Версіонування розкладів через окремі версії GTFS-фіду

Статус: прийнято, 2026-10-11

## Контекст

Система повинна виявляти зміни у розкладах громадського транспорту та сповіщати користувачів про них.

Для цього необхідно порівнювати поточний стан розкладу з попереднім. Потрібно визначити спосіб зберігання історії змін.

## Розглянуті варіанти

### 1) Зберігати лише актуальний стан розкладу

Переваги:
- проста схема бази даних;
- мінімальний обсяг збережених даних;
- швидший імпорт.

Недоліки:
- неможливо визначити, що саме змінилося;
- неможливо формувати сповіщення про зміни;
- відсутня історія розкладів.

### 2) Зберігати окремі версії розкладів

Переваги:
- можливість порівнювати розклади;
- підтримка історії змін;
- можливість генерувати повідомлення про зміни.

Недоліки:
- збільшення обсягу даних;
- складніша схема бази даних;
- необхідність підтримувати механізм порівняння версій.

## Рішення

Кожен успішно імпортований GTFS-фід зберігати як окрему версію розкладу (ScheduleVersion). Усі записи імпорту прив'язуються до конкретної версії.

## Наслідки

### Позитивні

- можна визначати зміни між версіями;
- підтримується історія розкладів;
- реалізуються повідомлення про зміни;
- можлива аналітика змін маршрутної мережі.

### Негативні

- збільшується обсяг бази даних;
- імпорт стає складнішим;
- необхідні додаткові запити для порівняння версій.

## Умова перегляду

Рішення переглядається, якщо система перестане підтримувати історію
змін або якщо постачальник даних надаватиме готовий механізм
версіонування та порівняння розкладів.
