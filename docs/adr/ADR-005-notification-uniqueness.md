# ADR-005. Одне сповіщення на одну зміну розкладу

Статус: прийнято, 2026-10-11

## Контекст

Користувачі можуть бути підписані на маршрути та отримуватисповіщення про зміни розкладу.

Під час повторного запуску задачі генерації повідомлень існує ризикстворення дубльованих сповіщень для тієї самої зміни.

## Розглянуті варіанти

### 1) Не контролювати дублікати

Переваги:
- найпростіша реалізація;
- відсутність додаткових перевірок.

Недоліки:
- користувач отримує однакові повідомлення;
- погіршується користувацький досвід.

### 2) Забезпечити унікальність на рівні бази даних

Переваги:
- неможливо створити дубльоване сповіщення;
- захист працює незалежно від коду застосунку.

Недоліки:
- потрібен додатковий індекс;
- складніше початкове проєктування схеми.

## Рішення

Використовувати унікальне обмеження для пари
(subscription_id, schedule_version_id).

## Наслідки

### Позитивні

- усунення дубльованих повідомлень;
- виконання вимоги про одне сповіщення на одну зміну;
- підвищення надійності системи.

### Негативні

- складніша схема бази даних;
- можливі помилки унікальності при неправильній логіці імпорту.

## Умова перегляду

Рішення переглядається, якщо система почне підтримувати різні типи сповіщень для однієї версії розкладу.
