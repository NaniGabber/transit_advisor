# ADR-002. Clean Architecture для структури застосунку

Статус: прийнято, 2026-10-11

## Контекст

Система містить імпорт даних, бізнес-логіку, API та доступ до бази даних. Необхідно забезпечити незалежність бізнес-логіки від технологій зберігання та способу взаємодії з користувачем.

## Розглянуті варіанти

### 1) Монолітна структура

Уся логіка розміщується поруч із контролерами та ORM-моделями.

Переваги:
- швидший старт розробки;
- менше файлів.

Недоліки:
- висока зв'язаність компонентів;
- складніше тестування;
- важче змінювати технології.

### 2) Clean Architecture

Поділ на шари:
- domain;
- application;
- infrastructure;
- interfaces.

Переваги:
- незалежність домену;
- простіше тестування;
- чіткий розподіл відповідальностей.

Недоліки:
- більше абстракцій;
- збільшення кількості файлів.

## Рішення

Організувати застосунок відповідно до принципів Clean Architecture.

## Наслідки

### Позитивні

- домен не залежить від FastAPI та SQLAlchemy;
- бізнес-логіка тестується окремо від БД;
- легше замінювати інфраструктурні компоненти.

### Негативні

- збільшується кількість проміжних об'єктів;
- потрібні додаткові mapper-и між шарами.

## Умова перегляду

Рішення може бути переглянуто для дуже невеликого проєкту без складної бізнес-логіки.
